Loops inside draw(): iterations and frames

  • Loops
  • Loops and draw()
  • Binary numbers
  • Loop extensions

Processing repeats draw(). A for loop repeats statements inside one function call. These are two different levels of repetition.

One complete call to draw() produces one frame. A loop inside that call completes before execution moves to the statements after it. A new loop iteration does not create a new frame.

1. Four circles, or one moving circle?

Predict this complete sketch. At the slow frame rate, will you see one new circle per frame or all four together?

void setup() {
  size(300, 200);
  frameRate(1);
}

void draw() {
  background(255);
  fill(0);

  for (int x = 40; x <= 160; x = x + 40) {
    ellipse(x, 100, 20, 20);
  }
}
Check your reasoning

All four appear together in each frame. Each call to draw() starts its own x at 40 and runs the whole loop. The next call clears the screen and draws the same four circles again.

2. Follow the first frame all the way through

  1. Processing calls draw().
  2. background(255) clears the drawing surface.
  3. fill(0) selects black.
  4. The loop creates its local x with value 40.
  5. The body draws at 40; the update makes x equal to 80.
  6. The body draws at 80, then 120, then 160, with a check and update each time.
  7. The update makes x equal to 200. The condition is false, so the loop ends.
  8. draw() reaches its closing brace. The completed frame is displayed.

The next call repeats this entire sequence. Processing updates the screen at the end of draw(), as explained in the draw() reference.

Across three calls there are twelve executions of ellipse(). Because the background clears each frame, only four circles are visible in the completed frame.

3. Observe the order in the console

In the first sketch, replace only draw() with this version. frameCount is Processing’s count of frames since the sketch started.

void draw() {
  background(255);
  println("Start frame " + frameCount);

  for (int x = 40; x <= 160; x = x + 40) {
    ellipse(x, 100, 20, 20);
    println("  x = " + x);
  }

  println("End frame " + frameCount);
}

frameRate(1) requests roughly one frame per second. It does not insert a one-second pause between loop iterations. A requested rate is a target, not a guarantee; see the frameRate() reference.

4. To animate, keep a value between frames

This second complete sketch draws one circle per frame. Predict its first five positions before running it.

int x = 40;

void setup() {
  size(300, 200);
  frameRate(1);
}

void draw() {
  background(255);
  fill(0);
  ellipse(x, 100, 20, 20);

  x = x + 40;
  if (x > 160) {
    x = 40;
  }
}

There is no inner loop. The function draws once, changes the stored position once, and returns. The next call uses the updated global value. At one frame per second, the motion appears as separate steps. Increasing the frame rate makes updates happen more often.

5. Scope explains the difference

In the four-circle sketch, int x = 40 belongs to the for statement. Every time execution reaches that statement, initialization runs again. The loop does not remember 200 for the next frame.

In the moving-circle sketch, the global x retains its value between calls. If you remove its global declaration and instead put int x = 40; at the beginning of draw(), each call draws at 40 again. The later update changes only that call’s local variable.

Try it

Try that local-variable change in the moving-circle sketch. Explain why the assignment still runs but the circle no longer moves across frames. Then restore the global variable.

6. Where background() goes matters

PlacementWhat it means
Once at the start of draw()Erase the previous frame, then construct the next one.
Inside the loop, before each shapeErase earlier iterations’ shapes; only the final shape remains in the completed frame.
Only in setup(), with no later clearingEarlier marks remain. New drawing accumulates on the surface.

Try it

In the four-circle sketch, move background(255) inside the loop, just before ellipse(). Predict what remains visible and explain why this still is not animation.

Check your reasoning

Only the circle at x = 160 remains. Each iteration erases the earlier circles, and the screen is updated after the entire draw() call. You do not see the erased intermediate versions as separate frames.

In the moving-circle sketch, clearing only in setup() leaves a trail. Drawing marks on the screen does not create a collection of independently moving objects.

7. You can use both kinds of repetition together

A loop can draw several elements in each frame while a global variable changes their shared position between frames. Trace the separate jobs of i and offset.

int offset = 0;

void setup() {
  size(360, 200);
  frameRate(10);
}

void draw() {
  background(255);
  fill(0);

  for (int i = 0; i < 4; i++) {
    int x = 40 + i * 40 + offset;
    ellipse(x, 100, 20, 20);
  }

  offset = offset + 2;
  if (offset > 120) {
    offset = 0;
  }
}

The counter i selects four positions within a frame. The global offset shifts the whole group between frames. The first frame draws at 40, 80, 120, 160; the second at 42, 82, 122, 162. Each frame still contains four circles.

Try it

Why is the offset update after the loop? Predict the effect of putting it inside the loop instead. Would all four circles still share the same offset within a frame?

Check your reasoning

After the loop, the shared offset changes once per frame. Inside the loop, it would change four times per frame, and later circles would use a different offset from earlier ones. That changes both the spacing and the rate of movement.

8. A loop must let draw() finish

This fragment never changes x. Trace it on paper; do not run it.

int x = 40;
while (x < 160) {
  ellipse(x, 100, 20, 20);
}

The condition stays true, so execution never reaches the end of the function. A loop like this inside draw() prevents completion of the frame and can make the sketch unresponsive. A very large terminating loop can also delay frames.

Do not use a waiting loop inside draw() to wait for a mouse press or a later frame. Let the function finish, then check input on a later call or handle it in an event function. Slowing execution with a delay inside the loop does not turn its iterations into completed frames.
